= pfdo_run: history
:toc:

== Abstract

pfdo_run was created in August 2020 as the pfdo family's member that runs a shell command per directory, grew its own `%tag` template language and per-job logging through 2021 and 2022, and was rebuilt in October 2026 as version 4 on pfdo 6, pftag 3 and hostlib 1, replacing its template language with pftag's, its string-substitution with per-argument resolution, and its own process handling with hostlib's.

== 2020: a command per directory

The first commit, on 24 August 2020, a week after pfdo's, made the base class's demonstration real: instead of touching files, run a command. The command needed to name the directory it was in, so pfdo_run gained the `%` tags that became the family's template idiom: `%inputWorkingDir`, `%outputWorkingDir`, `%inputWorkingFile`, and every command-line option by name. Version 2.0.0 in January 2021 brought the composed command line and manual, and 2.0.2 in February 2021 the per-job logging of stdout, stderr and return code into the output tree, which is the record a batch needs when one of a thousand runs fails.

== 2022: functions and the second grammar

Through 2022, 2.2.x and then 3.x, the template language acquired functions written as a prefix on the tag, `%_rmext_inputWorkingFile`, with `md5`, `strmsk`, `strrepl`, `rmext` and a Faker-generated `name`. In March 2023 the same idea was lifted into pftag as a package with a different grammar, functions after the tag; pfdo_run kept its own, and the two coexisted for three years.

== 2026: version 4

By 2026 pfdo_run carried the family's shared debts, `pfmisc`, `pudb` imported at module level, `Faker` and a process-wide `logging.disable` at import, a version read from installed metadata, no tests and no continuous integration, and several of its own. The command was substituted into as text and then split on whitespace, so a file with a space in its name broke the command or ran a different one. Stdout was read line by line and its last line dropped; stderr was read only after exit, so a chatty tool could deadlock. The `--noJobLogging` option gated the logs but was defined nowhere, so no job log had been written in years. The run's status was always reported False. The tag parser matched names by substring, so `%os` fired inside `%outputWorkingDir`, and `strrepl` ignored its arguments.

Version 4.0.0 rebuilt it on pfdo 6, pftag 3 and hostlib 1. The template grammar is pftag's: `%{inputWorkingDir}`, `%{inputWorkingFile|rmext}`; the engine's own parser is gone, and a 1.x-style `%name` fails the job with a message saying what to write. The template is split with `shlex` once and its tags resolved per argument with pftag's `argv_process`, then run without a shell. The first draft of 4.0 ran it with `subprocess.run`, which fixed the deadlock and the dropped line but gave up the live output 3.x had tried to offer; the comparison of that draft with the `jobber.py` copies in pl-dylld and a dozen other repositories led to hostlib, and 4.0 shipped on it: both streams read as they arrive, streamed to the console at `--verbosity 2`, the job's record carrying hostlib's envelope. Per-job records are written by default as `<file>-cmd`, `-stdout`, `-stderr` and `-returncode`, the stream files rendered as a terminal would show them. A failed template or a non-zero exit fails its directory and the run continues, and the status is truthful. The command line and manual are composed from pftree's and pfdo's parts and exposed again for pl-shexec, which is rebuilt on this version next.

Version 4.0.1 made the tags visible before the manual: the `--exec` help names the three per-file tags and points at the TAGS section, the description says that `%{...}` tags name the file in hand, and a template with no tag draws a warning that the same command would run for every file. Unlike awk or sed, whose language is their reason to exist, pfdo_run reads as a command runner, and a reader of `--help` could not have known that `--exec` carried a grammar.

Version 4.1.0 let a package built on pfdo_run name itself: `parser_build` takes `command` and `version`, so a ChRIS plugin wrapping the parser answers `--version` and `--help` as itself rather than as pfdo_run, the way `synopsis` already took `command`. pl-shexec 2.0 is the first such package.

Version 4.2.0 changed the default record from four files per job to one line per job. The four files, `-cmd`, `-stdout`, `-stderr` and `-returncode`, were pfdo_run 3's record because there was no other; under hostlib the record is the `JobResult`, which holds all four and the host, the timing and the errors besides, and the files had become a lossy copy of it in a form only `cat` reads. hostlib 1.2's `JsonSink` appends the whole record as one line of JSON, per directory to `jobs.jsonl`, which pflog 2's `pflog read` was already printing beside span lines; the four files stayed behind `--jobFiles` for the reader who opens a job's output in an editor, and `--noJobLogging` kept its meaning of no record at all.

Version 4.3.0 took pfdo 6.3 and pftree 4.2, whose `--man` and `--synopsis` print and exit as they are read, as `--version` does. `parser_build` attaches pfdo_run's page with `manual_attach`, and `main` no longer handles the flags after parsing. The occasion was pl-shexec, built on this parser, which could not answer `--man` without the `inputdir outputdir` that `chris_plugin` makes positional.
