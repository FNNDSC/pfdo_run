= pfdo_run: architecture
:toc:

== Abstract

pfdo_run is three small modules over pfdo, pftag and hostlib: `models` adds the command template and the job record to pfdo's options and re-exports the models of the layers below; `pfdo_run` is a `Pfdo` subclass whose analyze callback builds the command for each selected file and hands it to hostlib to run; `__main__` composes the command line and manual from pftree's, pfdo's and its own parts. The design has one load-bearing decision, that the template is split before its tags are substituted, and one deliberate delegation, that running the command, streaming its output and recording what happened are hostlib's and not reimplemented here.

== Options and records

`PfdoRunOptions` subclasses `PfdoOptions`, adding `exec` and `noJobLogging`, and inherits `fromDict`, so the whole argparse namespace passes straight through. `FileJob` records one file's job: the file, the command as built, a status, the errors that explain a failure, and `run`, hostlib's `JobResult` envelope when the command ran, with both streams, the exit status, the host's facts and the timing; `run` is `None` for a job whose template did not resolve, which is the one failure that happens before anything runs. It is a dataclass so that `RunResult.toDict()` expands it into the JSON a caller or pl-shexec reads; the analyze stage's `StageResult.payload["jobs"]` carries one per selected file. `pfdo_run.models` re-exports pfdo's `DirNode`, `StageResult`, `ProcessResult` and `RunResult` and hostlib's `JobResult` and `JobSpec`, so a tool built on pfdo_run imports from pfdo_run alone.

== Building a command

`PfdoRun.__init__` splits the `--exec` template once with `shlex.split`, so the user's quoting is honoured exactly once and a malformed template fails before any directory is touched. For each job, `job_run` builds a `Pftag` with two lookups: `options`, every field of the run's options stringified, which is how `%{outputDir}` works and why `exec` itself is left out; and `pfdo`, the three job tags. It then calls `argv_process` on the split template, which substitutes within each argument and never across argument boundaries. A value with a space stays inside its argument; a value containing a quote is just characters. The tagger runs `strict`, so an unknown tag, or a 1.x-style bare `%name`, fails the job before it runs, with the error in the job's record. The previous engine substituted into the string and then split it on whitespace, which is why a file with a space in its name broke it.

A fresh `Pftag` per job rather than one shared engine is what makes the analyze stage safe to thread: the lookups differ per job and nothing is mutated in common.

== Running it

The resolved argument list becomes a hostlib `JobSpec` and goes to hostlib's `job_run`, which starts the program without a shell, reads both output streams concurrently from the first byte, waits, and returns a `JobResult`. The previous engine read stdout line by line and stderr only afterwards, which dropped stdout's last line and could deadlock on a process that filled its stderr pipe; hostlib exists so that this is written once. A program that cannot be started is a failed run that never got an exit status, and a non-zero exit is a failed run that did; both carry their reason in `errors`, which `FileJob` copies up.

Where the output goes while the command runs is `sink_build`'s decision, made per job from the options: a hostlib `JsonSink` on `<outputPath>/jobs.jsonl` unless `--noJobLogging`, which appends the job's whole record as one line of JSON when it ends, both streams raw, so a directory's jobs are one file a reader parses line by line; with `--jobFiles` also a `FileSink` on `<outputPath>/<file>`, which writes `<file>-cmd`, `-stdout`, `-stderr` and `-returncode` as the job runs and, when it ends, rewrites the two stream files as a terminal would have shown them, so a progress bar redrawn a hundred times is one line on disk while the record keeps every frame; a `ConsoleSink` when `--verbosity` is 2 or more, so a long job can be watched; a tee of whichever apply; or nothing. Under `--threads` the analyze stage runs directories concurrently, and since one directory's jobs run in sequence its `jobs.jsonl` needs no lock; the console streams of concurrent jobs interleave, which is the honest view of concurrent work. In 3.x `--noJobLogging` was documented but never defined, so the logs were never written.

== The stages

`inputRead_callback` creates the directory's output path and passes the files on. `inputAnalyze_callback` runs one job per file that `filesToAnalyze` selects and returns a `StageResult` whose status is True only when every job succeeded; pftree then drops a failed directory from the tree and continues. There is no save callback, because the commands have already written their results, and under pfdo 6.1 a stage a subclass does not override does not run, so nothing is overridden to suppress it and `run()` processes because callbacks are overridden.

== The command and the manual

`parser_build` composes pftree's `parserIO_build()` and `parserCore_build("pfdo_run", version)`, pfdo's `parserSelf_build()` and pfdo_run's own; `standalone=False` omits the I/O parent for a ChRIS plugin that supplies positional directories. The manual composes pftree's and pfdo's texts with pfdo_run's `--exec` and `--noJobLogging` descriptions and a TAGS section that points at pftag's reference, and `synopsis(command=...)` takes the command's name so pl-shexec prints its own. The page is rendered through `pftree.manual`.

== Verification

The tests run real commands on a fixture tree with nested directories and a file name containing a space: copying every file with records, `--noJobLogging`, `--analyzeFileIndex f`, captured stdout with the host facts in the envelope, a command that fails in some directories and not others, an unresolved tag, a 1.x template, a missing program, options as tags, threads against sequential, the job lookups, an empty template, output streamed to the console at `--verbosity 2` and silent below it, a carriage-return progress line rendered to one line on disk while the envelope keeps the frames, the sink chosen for each combination of options, the models re-exported from pfdo and hostlib, and JSON readiness. The command is tested through `main`. Continuous integration mirrors pftree's.
